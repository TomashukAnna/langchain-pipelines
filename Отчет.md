# Лабораторная работа № 1. Пайплайны обработки данных на основе LangChain и LLM


## Цель работы

Разработать интерфейс поиска товаров в SQLite по запросам на естественном языке. Освоить параметризованные цепочки LangChain, структурированный вывод, валидацию Pydantic, вызов инструментов, повторную генерацию при ошибках и хранение состояния диалога вне модели.

## Архитектура

Чат принимает реплику пользователя и передает ее в параметризованный промпт вместе с последним валидным состоянием поиска. Qwen формирует параметры `category`, `max_price` и `sort_by`. В обычном режиме `PydanticOutputParser` разбирает JSON и проверяет его по схеме `ProductQuery`. В режиме `/tool` приложение извлекает аргументы из `tool_calls` и проверяет их через `ProductQuery.model_validate()`.

После проверки функция Python формирует запрос к SQLite. Категория и цена передаются через параметры `?`, направление сортировки выбирается из фиксированного словаря. Для категории `other` поиск пропускается. Чат выводит товары с ценами или сообщение о пустой выдаче. При ошибке парсинга в обычном режиме `with_retry` повторяет генерацию и разбор, максимум до 3 попыток. Журнал фиксирует вызовы, валидацию и поиск. Токен считывается из переменной окружения.

## Часть 1. Базовая цепочка LangChain

Цепочка `ChatPromptTemplate | llm | StrOutputParser` подставляла `query` в пользовательское сообщение, а `language` - в системное. Прямой вызов вернул `AIMessage`, цепочка - текстовый результат типа `TextAccessor`, преобразуемый в строку через `str()`. Методом `batch` обработаны три запроса. Модель соблюла заданный язык во всех трех случаях, но верно определила категорию в двух. Планшет для чтения она отнесла к электронным книгам (`E-Readers`).

## Часть 2. Структурированный вывод

Схема `ProductQuery` ограничивает перечень категорий и порядок сортировки, допускает неотрицательный целочисленный предел цены или `null`. По умолчанию цена не ограничена, сортировка идет по возрастанию. Инструкции формата включены в системный промпт, а проверенный объект сериализуется в JSON.

В 2.3 все семь запросов прошли валидацию и совпали с ожидаемыми параметрами по всем 21 проверкам полей. Модель преобразовала «до 50 тысяч» в 50 000, выбрала сортировку по убыванию для дорогих смартфонов и вернула `other` для холодильников. В запросе «Хочу что-нибудь для чтения, тысяч за 30» назначение было явно указано, а тип товара - нет. Модель выбрала `other` и интерпретировала примерный бюджет как предел в 30 000 ₽. Для «недорогих смартфонов с хорошей камерой» модель оставила цену без лимита и выбрала сортировку по возрастанию. Качество камеры схема не описывает.

### 2.4. Сравнение режимов размышления

| Запрос | Thinking выключен | Thinking включен | Параметры в обоих режимах |

| Покажи недорогие смартфоны с хорошей камерой | 0,346 с, 31 выходной токен | 1,511 с, 150 выходных токенов | `smartphone`, `null`, `price_asc` |

В обоих сравнениях thinking увеличил время и число выходных токенов, а параметры остались прежними. Категория `tablet` в первом запросе отличалась от результата 2.3 в обоих режимах. Все четыре ответа разобраны успешно. В одном случае JSON был обернут в блок Markdown. Рассуждение в `content` не наблюдалось, отдельного поля с ним клиент не показал, число токенов рассуждения было недоступно. По этим данным нельзя определить, где сервер хранит рассуждение и сколько токенов на него потрачено. Если рассуждение передается клиенту, его следует отделять от итогового JSON, чтобы разбор не зависел от произвольного текста.

### 3.4. Поиск через инструмент

Модель предложила вызов `search_products` во всех семи запросах, и все аргументы прошли валидацию. Для холодильников приложение пропустило поиск. В шести ответах поле `content` было пустым, а в запросе про чтение текст сопровождал вызов. Ветка ответа без вызова предусмотрена в коде и в этих семи запусках не сработала.

В части 2 схема `ProductQuery` передавалась как инструкция формата в системном промпте. `PydanticOutputParser` извлекал JSON из `content` и передавал данные на проверку Pydantic. В 3.4 схема передавалась через `args_schema` и `bind_tools`. Сервер разбирал вызов инструмента, LangChain предоставлял аргументы в `tool_calls`, а приложение явно валидировало их и выполняло поиск. Результат поиска модели не передавался.

Параметры совпали с 2.3 в пяти случаях из семи. Для чтения модель выбрала планшет вместо `other`, а для недорогих смартфонов сама задала предел 30 000 ₽ вместо `null`. Оба ответа прошли проверку схемы, поскольку значения допустимы. Такой результат требует отдельной оценки по смыслу.

## Часть 4. Ошибки, повторные попытки и журнал

| Тестовый ответ | Исходное исключение | Этап и причина |
|---|---|---|
| Две запятые подряд в JSON | `JSONDecodeError` | Синтаксический разбор останавливается до проверки полей. |
| `category = "fridge"` | `ValidationError`, `literal_error` | JSON прочитан, но категория отсутствует в допустимом перечислении. |
| `max_price = -1000` | `ValidationError`, `greater_than_equal` | JSON прочитан, но цена нарушает ограничение `max_price >= 0`. |

Во всех трех случаях внешнее исключение было `OutputParserException`, а исходная причина доступна через `__cause__`. Поэтому `with_retry` обрабатывает оба типа сбоев, повторяя только генерацию и разбор. При исчерпании попыток приложение предлагает уточнить запрос.

| Сценарий с тестовой моделью | Вызовы модели | Запуски SQLite | Результат |
|---|---:|---:|---|
| Без retry, первый JSON некорректен | 1 | 0 | Сообщение об ошибке |
| С retry, второй JSON корректен | 2 | 1 | Lenovo IdeaPad 3 и Acer Aspire 5 |
| С retry, все три ответа некорректны | 3 | 0 | Сообщение об ошибке после исчерпания попыток |

Фрагмент журнала успешного повтора:

```text
[Попытка 1/3] Вызов LLM.
[Попытка 1/3] Разбор или проверка не прошли (JSONDecodeError).
[Попытка 2/3] Вызов LLM.
[Попытка 2/3] JSON разобран.
[Валидация] Параметры приняты. {"category":"laptop","max_price":50000,"sort_by":"price_asc"}
[Поиск] Выполняется запрос к SQLite.
[Поиск] Найдено товаров: 2.
```

На этих диалогах хранение текущих параметров сэкономило 214 входных токенов при одинаковой точности. При смене категории модель сбросила бюджет и сортировку в обоих вариантах. Валидация пропустила ответ, поскольку он соответствовал схеме, хотя нарушал правило сохранения параметров.

## Контрольные вопросы

1. Чем пайплайн из этой работы отличается от агента, в котором LLM сама решает, какую функцию вызвать и что делать с результатом?

*Ответ 1: В работе порядок действий задан в коде,а в агенте модель может самостоятельно выбирать между инструментами, получать результаты их работы и на их основе решать, какой шаг сделать дальше.*

2. Как формируются цепочки в LangChain и что делает `StrOutputParser`?

*Ответ 2: Компоненты цепочки соединяются оператором |. Слева направо: словарь с запросом → готовые сообщения → ответ модели → текст. StrOutputParser достает текст, поэтому у результата цепочки уже не нужно брать .content.*

3. Зачем нужны системное и пользовательское сообщения?

*Ответ 3: Системное сообщение задает роль модели, правила обработки запроса и формат ответа. Пользовательское сообщение содержит сам запрос. Такое разделение позволяет использовать одну и ту же инструкцию для разных запросов.*

4. Что такое Structured Output и чем он отличается от произвольного текстового ответа?

*Ответ 4: Это ответ с заранее определенными полями и типами данных. В нашей работе программа ожидает категорию, верхнюю границу цены и направление сортировки. Из такого ответа можно сразу взять значения для поиска. При ответе свободным текстом их пришлось бы дополнительно извлекать из фразы.*

5. Для чего используются `BaseModel`, `Field` и `Literal` в Pydantic?

*Ответ 5: BaseModel позволяет описать Pydantic-модель, которая проверяет входные данные. Field задает описание поля, ограничения и значение по умолчанию. Literal перечисляет допустимые значения, например price_asc и price_desc для сортировки.*

6. Почему LLM без доступа к базе не может надежно ответить на вопрос о товарах каталога?

*Ответ 6: У модели нет сведений о том, какие строки записаны в конкретном каталоге. Она начинает придумывать то, чего на самом деле может и не быть.*

7. Чем получение параметров через вызов инструмента отличается от инструкций формата в промпте? Что делает парсер вызовов на сервере и что остается за приложением?

*Ответ 7: При инструкции формата модель возвращает JSON в поле content, а PydanticOutputParser извлекает и проверяет параметры. При вызове инструмента схема передается вместе с описанием search_products. Серверный парсер распознает вызов в ответе модели и выделяет его имя и аргументы, которые LangChain показывает в tool_calls. Приложение проверяет аргументы через ProductQuery.model_validate() и решает, можно ли выполнить поиск.*

8. Почему структурированный ответ необходимо валидировать до обращения к классическому ПО? Почему не следует исполнять SQL, сгенерированный LLM, без ограничений?

*Ответ 8: Валидация нужна, чтобы в поиск попадали только допустимые категории, значения цены и варианты сортировки. Если разрешить модели составлять SQL, она может ошибиться в запросе или сформировать команду, которая читает лишние данные либо изменяет базу.*

9. Какие ошибки должен обрабатывать механизм retry? Чем повторная генерация с тем же промптом отличается от исправления ответа с учетом предыдущей ошибки?

*Ответ 9: retry срабатывает при OutputParserException, когда JSON не удается разобрать или данные не проходят проверку Pydantic. Повтор с тем же промптом дает модели еще одну попытку. При исправлении с обратной связью модели дополнительно передают предыдущий ответ и описание ошибки, чтобы она знала, что исправить. В нашей цепочке максимум три попытки, а поиск запускается только после успешной проверки.*

10. Где хранить состояние диалога и что передавать модели на каждом шаге?

*Ответ 10: Состояние хранится в приложении. В нашем чате это последний валидный объект ProductQuery, который передается модели вместе с новой репликой. Если ответ не прошел проверку, прежнее состояние сохраняется. Передача полной истории тоже возможна.*
